# Wingcommander Component Library

`thekpihub-wingcommander-frontend` ships a small, real component library inside this app —
12 shadcn/Radix-UI primitives, themed to KPI Hub's gold-on-navy brand. They're consumed two
ways: directly by the app itself (`src/components/ui/*`), and as a packaged build
(`npm run build:lib`) that [`/design-sync`](https://claude.ai/design) reads to keep
[claude.ai/design](https://claude.ai/design/p/02211231-7100-42d6-9d91-61635511d84a)'s
"Wingcommander Design System" project in sync with the real code.

This doc is for engineers working on this repo or its design-system sync — not for the
design agent (that's `.design-sync/conventions.md`, which is short by design).

## Components

`Avatar`, `Badge`, `Button`, `Card`, `Dialog`, `DropdownMenu`, `Input`, `ScrollArea`,
`Separator`, `Tabs`, `Textarea`, `Tooltip` — each in `src/components/ui/<name>.tsx`. Subparts
(`CardHeader`, `DialogTrigger`, `TooltipProvider`, etc.) are exported from the same files and
meant to be composed inside their parent, not used standalone.

## Why a separate library build exists

The app itself (`vite.config.ts`, `npm run build`) builds a deployable bundle, not an
importable package — no `.d.ts` output, no stable entry point. `npm run build:lib` (new,
added for the design-sync work) builds the *same source* a second way: a real ES module
entry (`dist-lib/index.es.js`) with full TypeScript declarations (`dist-lib/index.d.ts`) and
a compiled stylesheet (`dist-lib/style.css`). Nothing about the app build changed — this is
strictly additive.

**Advantages of having this:**
- The components are now a real, typed, importable unit — usable from a future separate
  app, a Storybook, or any other tool that wants the design system without copy-pasting
  source files.
- It's what makes the `/design-sync` to claude.ai/design possible at all — the sync tooling
  needs a built `dist/` entry + matching `.d.ts` tree, which didn't exist before.
- It costs nothing to maintain day-to-day: it's a separate script (`build:lib`), separate
  output directory (`dist-lib/`, gitignored), and doesn't run as part of `npm run build` or
  any deploy step.

## Install & build

From the repo root (npm workspaces — `frontend` and `backend`):

```sh
npm ci                       # install everything once, from the root lockfile
cd frontend
npm run build:lib            # builds dist-lib/index.es.js, dist-lib/index.d.ts, dist-lib/style.css
```

To use a component elsewhere in the app, just import from the existing source path — you
don't need the library build for that:

```tsx
import { Button, Card, CardHeader, CardTitle } from "@/components/ui";
```

The library build (`dist-lib/`) only matters for tooling that consumes the package from
outside this app (currently: the design-sync importer). You don't need to run
`build:lib` for normal app development.

## Re-running the design-sync

The sync to claude.ai/design lives under `.design-sync/` (config, conventions, notes — all
committed) and `.ds-sync/` (staged converter scripts + their own `node_modules` — gitignored,
regenerated by copying from the skill's bundled scripts). To re-sync after changing a
component:

```sh
cd frontend
npm run build:lib
node .ds-sync/resync.mjs --config .design-sync/config.json \
  --node-modules ../node_modules --out ./ds-bundle \
  --remote .design-sync/.cache/remote-sync.json   # fetch this from the project first
```

See `.design-sync/NOTES.md` for the repo-specific gotchas (why certain Radix subparts are
excluded from the top-level component list, the Playwright version pin, font handling, etc.)
before touching `.design-sync/config.json`.

## Troubleshooting

**`npm run build:lib` fails with a TypeScript rootDir error.**
The library entry is `src/index.ts` (package root), not nested under
`src/components/ui/`. If you move it, the emitted `.d.ts` will land in the wrong place
relative to `index.es.js`, breaking anything that expects them as siblings — including the
design-sync converter.

**A new component doesn't show up in the design-sync output, or shows up as several extra cards.**
Radix compound components in this codebase export subparts as flat names
(`DialogTrigger`, not `Dialog.Trigger`), so the converter can't automatically tell a subpart
from a real component. New top-level components are picked up automatically; new *subparts*
need an entry in `.design-sync/config.json`'s `componentSrcMap` (set to `null`) or they'll
appear as their own standalone card.

**A component's styling looks unstyled or wrong in the synced preview.**
Check that the class/utility it uses actually exists in `dist-lib/style.css` after a fresh
`build:lib` — Tailwind only emits classes it sees referenced in scanned source files, so a
class that's only used in unrelated parts of the app (e.g. `.glass-dark`, used outside
`components/ui/`) won't appear in the library's compiled CSS even though it's defined in
`src/index.css`. This is expected, not a bug — see `.design-sync/NOTES.md`.

**Render check fails locally with `[RENDER_SKIPPED]` or a Playwright launch error.**
The render check needs Playwright + a matching cached Chromium build. This repo's sync was
last run pinning `playwright@1.60.0` (Chromium revision 1223) to match what was already
cached on the machine that ran it — a different machine may need a different
pinned version, or just `npm i -D playwright && npx playwright install chromium` for a fresh
install with no pre-existing cache to match.

**An overlay component (`Dialog`, `DropdownMenu`, `Tooltip`) renders empty or escapes its card in the synced preview.**
These use Radix portals, which render outside the normal component tree — they need
`defaultOpen` (or the menu/tooltip equivalent) set in the authored preview so they show their
open state without interaction, and a `cardMode: "single"` + fixed `viewport` override in
`.design-sync/config.json` so the open content renders inside the card instead of escaping it.
